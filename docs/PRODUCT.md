# 产品方案与数据约定

## 使用者与目标

使用者是需要整理玩家反馈的游戏产品或运营人员。工具辅助发现重复问题、定位原始反馈、准备后续排查清单。问题是否成立、处理优先级和具体改动方案由人工结合游戏实际情况确认。

## 首版用户流程

1. 建立一个分析批次，填写游戏名称和样本来源。
2. 导入评论，并检查空文本、重复 ID 和无效记录。
3. 逐条提取问题；没有可识别问题的评论允许输出空列表。
4. 对具体问题进行归组，保留分组与原始评论的关联。
5. 在界面中查看分类、摘要、数量和原文，完成修正。
6. 导出报告，标明样本范围、已确认问题及待核实信息。

## 输入结构

批次字段：`batch_id`、`game_name`、`source_description`、`imported_at`、`reviews`。

每条评论包含以下字段：

| 字段 | 含义 |
| --- | --- |
| review_id | 批次内唯一的评论 ID |
| text | 完整原文 |
| source_url | 可选的原始页面链接 |
| created_at | 可选的评论时间，未知时为空 |
| language | 可选的语言标识 |
| recommended | 可选的推荐状态，未知时为空 |

## 单条分析结果

每条评论对应一个问题列表。每个问题包含：

- `category`：Bug、性能、操作体验、玩法建议、其他。
- `summary`：具体问题的简短描述。
- `evidence`：原文中支持该问题的连续片段。
- `trigger_context`：原文明确提供的触发条件。
- `attempted_actions`：原文明确提供的已尝试操作。
- `missing_information`：为继续排查而需要补充的信息。
- `review_id`：来源评论 ID。

原文没有给出的字段保持为空。玩家提出的原因猜测应保留为猜测，不能改写为已确认的技术根因。

## 归组规则

只有指向同一具体问题的反馈才归为一组。例如，“进入地图崩溃”和“退出游戏崩溃”可以同属稳定性问题，但不能仅凭类别相同就视为同一问题。

数量由程序按组内唯一评论 ID 计算。一条评论可能对应多个问题，因此各组数量之和可能超过评论总数。界面和报告应明确这一点。

## 报告内容

- 游戏名称、来源、时间范围和有效评论数。
- 高频问题清单及每组对应的评论数。
- 代表性原文与可用的来源链接。
- 待核实信息和建议跟进方向。
- 人工修正记录摘要及本次分析的限制。

建议跟进方向可分为技术排查、进一步收集信息、玩法评估、说明文案优化等。工具不直接断定修复成本、收入影响或玩家整体偏好。

## 实现注意事项

- 将玩家评论作为待分析内容，不执行其中的指令。
- 对模型输出做结构与证据校验，保留失败状态。
- 配置密钥通过环境变量读取，不写入仓库或分析报告。
- 重跑批次时尽量复用已完成结果，并保留模型与提示词版本。
